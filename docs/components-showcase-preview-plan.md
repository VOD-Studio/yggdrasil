## 1. 要交付的结果

用户在组件图鉴中应当直接看见组件实际的界面，并在详情页体验适合公开演示的交互。当前仅显示名称、图标、源码路径的 19 个条目，必须全部补齐。

核心要求是复用：正式页面和图鉴调用同一份展示实现。需要权限、请求或持久化的部分由正式页面负责；图鉴提供固定样例和本地状态。只有图鉴调用的新仿制界面，即使外观相似，也不满足要求。

完成后应当具备：

- 目录卡片能辨认出每个组件的主要结构；组件不是始终关闭的弹窗、空编辑器或一直加载的骨架。

- 素材、评论和运行器的演示操作明确标识为本地演示，不产生真实业务写入。
- 已有 64 个预览继续正常工作。
- 正式页面继续使用原来的认证、数据获取和业务操作，并经过针对性回归。
- 本地实现、生成资源、验证记录和分组提交齐全。推送、发布和部署不在本任务范围内。

## 3. 产品行为

### 3.1 目录卡片

保持现有图鉴的整体布局、分类和入口，替换卡片的预览内容。

- 首次可见时展示最能识别组件的状态，例如选中两张图片的素材库、包含文件状态的上传面板、带代码和输出的运行器。
- 弹窗卡片展示共用的面板内容，不在列表加载时打开全屏遮罩。
- 布局卡片展示头部/侧栏/正文/页脚的关系，正文使用简短样例，不嵌套当前图鉴路由。
- 简单组件保留现有轻量交互。复杂卡片以可读的展示为主，完整交互放到详情页。
- 源码路径留在文档区域，不能继续成为预览主体。
- 宽界面可以在有界窗口中缩放，但文字和关键控件须可辨认。按组件确定合理宽高，不用同一个裁切规则硬套文章、弹窗和终端。
- 浏览器库加载前使用有尺寸的占位，加载失败显示可重试状态；就绪后必须出现真实实例。

### 3.2 详情页

详情页采用足够大的预览区域，控件应能直接使用，避免把缩略卡片原样放大后仍然无法操作。

- 交互预览显示与该组件相关的少量状态选项，例如单选/多选、空列表/有数据、默认/失败。
- 静态组件使用“组件预览”或“样例展示”，不显示无效的交互提示和重置按钮。
- 业务演示区使用简短说明，例如“本地演示，内容不会保存”。运行器的固定输出明确称为“输出示例”。
- “恢复默认”真正重置当前演示的查询、选择、草稿、输出、错误等状态；关闭属于该演示的浮层并停止未完成的演示任务。
- 优先通过给当前预览子树更换 key 来复用正常的卸载/重新挂载流程；外置的 Checkbox 等属性信号同步复位。重置范围仅限当前预览，不能重置目录筛选或整页主题。
- 返回目录保留分类、搜索条件和滚动位置。
- 原有代码复制和高亮继续有效。新增示例能让读者理解正式组件怎么使用，不用展示函数签名冒充完整调用示例。

### 3.3 预览能力与文档类型

移除 `kind == reference` 对预览行为和交互文案的控制。

推荐给目录数据添加有 Rust 枚举约束的 `preview_mode`，取值为 `interactive`、`static`；含义以详情页能力为准。目录卡片是否延迟挂载是实现策略，不额外暴露为用户标签。

- 对所有现有条目明确填写模式；不要默认把遗漏值解释为可交互。
- 目录和详情页使用同一份模式数据，不再分别维护组件名称白名单来决定文案。
- Rust 调用示例、接口说明、浏览器调用示例属于文档类型，单独处理，不从预览模式推断。
- 预览渲染按稳定 slug 分派；目录有条目而没有对应渲染时，检查必须失败，不能静默落回通用示意卡。
- 组件数量和必要的预览统计从目录计算，移除容易过期的手写数量。

## 4. 实现结构与共用代码

### 4.1 数据与展示的连接位置

```text
正式入口：认证、请求、持久化、业务回调 ─┐
                                      ├─ 共用展示实现
图鉴入口：固定资料、局部状态、演示回调 ─┘
```

直接可以接收样例 props 的组件继续直接调用。对依赖业务行为的组件，按需要提取共用面板、表单或布局壳；正式入口也必须改为调用它。

提取后的展示部分接收显示所需的数据和事件回调，不在内部调用认证、上传、评论提交、执行接口或业务存储。客户端编辑器、弹窗焦点和局部交互等必要 UI 行为可以保留，但必须有明确生命周期。

具体约束：

- 复用现有类型、纯函数和选择逻辑。只有服务 DTO 不能表达展示数据时，才添加小的显示数据类型。
- 保留正式组件的公开调用方式；必要的新参数应有兼容的默认行为，并更新所有受影响调用方。
- 内部共用展示函数使用满足调用关系的最小可见性，避免把内部实现误纳入“新增公开组件”目录。
- 不建立通用模拟后端、通用依赖注入框架或新组件平台。
- 不用散落在各层的 `is_preview` 条件来关闭请求。
- 不通过复制正式 RSX/CSS、截图、画一份相似界面完成验收。
- 不把整页 iframe 或全局 fetch 拦截当作默认演示实现。测试拦截只用于检测越界请求和故障注入，不能代替组件本身的隔离。

### 4.2 文件组织

保留 `src/pages/components_showcase.rs` 作为目录和详情页入口。新增代码较多时可拆出：

```text
src/pages/components_showcase.rs
src/pages/components_showcase_data.json
src/pages/components_showcase/
    fixtures.rs          # 固定文章、评论、素材、输出示例
    previews.rs          # 演示状态、场景组合与预览分派
    browser_previews.rs  # 浏览器实例宿主、挂载和清理
```

这是建议的最小拆分，不要求为每个条目创建文件。共用展示实现放回对应的 `src/components/` 文件或其邻近模块；正式组件不能反向依赖 `pages::components_showcase`。

样例资料只包含仓库自带图片、固定文本和本地身份。图片使用真实存在的静态路径，不假设数据库中有特定素材，不构造不存在的 `/uploads/...` 路径。

## 6. 必须处理的技术细节

### 6.1 SSR、ID 和路由

- SSR 和 WASM 首次渲染使用同一份固定资料、初始状态及确定的 DOM ID。
- ID 使用稳定的“用途 + slug + 局部角色/序号”；避免随机值、当前时间和两端执行顺序不同的全局计数器。
- `Header` 目前固定使用 `mobile-nav-menu`。页面原生 Header、Header 样例和 FrontendLayout 样例同时存在时，菜单 ID 与 `aria-controls` 必须各自对应。
- 布局样例不能复制真实页面使用的唯一 `data-vt-shell` 标记、滚动恢复标记或过渡名称。将这类职责留在正式页面封装，避免导航协调器误认样例为页面外壳。
- 布局壳接收 children；图鉴不会挂载 `Outlet<Route>`，不会引入递归图鉴或后台登录跳转。

### 6.2 DOM、目录与弹窗的作用域

- `PostContent` 当前会使用全局 `.post-content`、锚点和灯箱初始化。预览增强应接受根元素/限定选择器，不能让一个样例重新初始化整页。
- `toc-sidebar.ts` 当前只有一个 `disposePrev`，且从 document 查找第一个目录。需要支持指定目录、正文和滚动容器，并按实际实例清理；保留正式文章的默认调用行为。
- 目录中的标题 ID 和锚点限定到样例，点击后不改变图鉴的导航 hash 或滚动位置。
- 缩放一个 700px 容器不会改变 CSS 的 viewport 媒体查询。移动布局须在真实窄 viewport 下验收；若做桌面/手机演示切换，需要显式支持容器布局，不能仅修改宽度就宣称已经切换断点。
- 卡片展示共用弹窗面板时不使用 `aria-modal`、全屏遮罩或全局 Escape 监听。用户在详情页点击打开后，才挂载真实 `ModalShell`。
- `ModalShell` 当前用全局首个 `[data-ygg-modal-panel]` 找焦点。确认实际打开的面板获得焦点，关闭后回到触发按钮；内嵌缩略面板不能匹配到错误目标。
- `inert` 不阻止挂载副作用、网络请求或全局监听，不能作为数据隔离机制。

### 6.3 加载和清理

- 重型卡片首次进入可视范围时才请求编辑器库并挂载；简单基础组件不因此被改造成复杂懒加载框架。
- 已挂载的卡片在当前目录挂载周期内保留实例，避免滚动边缘反复创建/销毁；筛选移除卡片、离开目录或详情时销毁。
- 浏览器库共享资源加载结果，但每个预览拥有独立容器和实例。
- 等库就绪且宿主 DOM 存在后再构造 JS Options/实例；SSR 只输出有界宿主与占位，迟到的加载结果不能复活已离开的预览。
- 加载失败的重试复用现有 `LibraryLoadError` 及加载器能力。
- 所有实例、Closure、Observer、事件监听和演示任务均随所属预览清理；不要用 `Closure::forget` 留下永久回调。
- 核对 JS `_instances` 注册表：当前 Rust Drop 调用 destroy，但这不等于注册表已移除引用。若增加频繁挂载，保证旧实例从注册表正确移除；销毁旧实例不能误删同 ID 的新实例。
- 灯箱初始化要保留其他使用方的配置；离开正在打开灯箱的演示时，关闭该演示拥有的浮层并清理关联监听。

### 6.4 样例状态与副作用

- 图鉴不伪造已登录的全局 `UserContext`，不改真实账号状态。
- 评论演示状态在预览内存中保存，不借用真实文章 ID 对应的缓存键，不调用待审核状态轮询。
- 图片演示使用静态本地资源；本任务默认不采集用户文件。以后若增加本地 File 预览，须单独处理 Object URL 回收。
- 输出示例是固定演示数据，不执行或解释用户输入的程序；预览按钮与快捷键都受相同回调约束。
- 重置或离开时取消播放/延时任务，防止旧任务向重置后的新状态写入。
- 主题继续由全站主题系统驱动，演示内部不覆盖全局主题设置或另造主题存储。

## 8. 验证方案

### 8.1 检查应当覆盖什么

保留并运行现有目录完整性、素材选择顺序/去重、上传校验、正文解析、浏览器库及导航相关测试。新增检查只针对本次实际风险：

1. **预览覆盖**：目录每个条目都有可识别的渲染与合法模式；这 19 个条目渲染出对应的主要界面结构，不能仅断言文字名称存在或枚举值非空。
2. **共用展示**：代码复核确认正式入口与演示入口调用相同展示实现。SSR/DOM 检查与浏览器截图辅助验证外观，不能用元数据测试代替这一点。
3. **局部交互**：选中顺序、评论回复/草稿、重置后旧任务停止等，在实际使用的接口处增加最小回归。
4. **作用域**：多 Header 的 ID、两个目录实例的互不影响、灯箱与预览根节点的限定。
5. **生命周期**：库加载失败后可重试，离开后迟到结果不会挂载，重复进入不会累计失效实例与监听。

提取展示层时生产控制逻辑应尽量保留。若确实改变了请求时序、回调触发或存储入口，补对应回归后再继续。

### 8.2 浏览器验收脚本

建议新增 `scripts/test-components-showcase.cjs`，沿用 `scripts/test-view-transitions.cjs` 的 Node + Playwright 调用方式，不引入新的测试框架。脚本连接已经运行的站点，不隐式启动/停止服务、不创建真实业务记录。

建议环境变量：

- `SHOWCASE_BASE`：待验收站点的实际同源地址，例如 `http://127.0.0.1:8080`。
- `PLAYWRIGHT_MODULE`、`CHROMIUM_PATH`：与已有脚本保持一致；本机已有模块和浏览器时可省略。
- `SHOWCASE_ARTIFACT_DIR`：截图和报告输出目录，默认使用现有忽略规则覆盖的目录或系统临时目录。

脚本至少覆盖：

- 19 个详情页逐个直接打开，确认加载完成、主要结构存在、没有通用示意卡；全部详情页桌面浅色检查。
- 目录筛选逐组展开，滚动使目标卡片进入可视范围，确认真实预览出现。
- 19 个详情页手机宽度、深色模式下的布局与横向溢出检查；交互用例覆盖每种依赖/宿主模式，无须为每个静态标签穷举组合。
- 关于 → 图鉴 → 详情 → 返回；搜索/分类/滚动状态恢复，连续切换详情，浏览器前进后退。
- 素材选择确认、上传状态切换、评论本地提交与回复、运行器播放输出、灯箱打开关闭、各演示恢复默认。
- 编辑器及终端页面往返至少 5 次，检查实例数量回到预期范围、无重复回调或已销毁实例异常。
- 冷浏览器上下文中，未进入重型卡片可视区域且未打开重型详情前，Tiptap/CodeMirror/Xterm 不被图鉴提前加载。Lightbox 和站点 core 当前本来就全局加载，不把它们误判为新增提前加载。
- 一个代表性的库加载失败/重试场景；一个加载中立即离开的场景。
- 真正的窄 viewport（例如 390px）和桌面 viewport（例如 1440px），明暗主题、减少动态效果；检查弹窗 Escape、焦点回归及键盘访问。

### 8.3 网络和存储验收

监测匿名访问和上述所有演示操作，确认没有由图鉴新增的认证探测、后台素材/上传配置、评论读取/提交/待审核轮询、上传、代码执行或 SSE 请求。

不要把所有 `/api/` 或所有 POST 都一律认定为写操作：Dioxus server functions 和现有站点页脚可能有合法读请求。先确认正常前台布局的请求基线，再按实际 server function 对应路径识别业务请求。报告中写明检查到的接口，不能只写“没请求后端”。

测试若为防止误写而拦截这些接口，必须记录调用尝试并使检查失败；拦截成功不代表组件已经隔离。禁止用全局请求 mock 让正式控制器看起来正常工作。

评论相关 localStorage 项在前后保持一致；用户主动切换主题等正常全站操作单独看待，不要求所有存储字节完全不变。报告与日志不包含 Cookie、Token 或用户隐私内容。

### 8.5 构建和检查命令

按根目录 `AGENTS.md` 使用本地工具，缺少必要工具时再用仓库 Docker 兜底。以下是完成实现后的检查，不要求规划阶段执行：

```bash
make check-dev-tools
```

修改过 `libs/` 时重建 JS/CSS bundle；修改过 `input.css` 或共享组件 class 时重建 Tailwind：

```bash
make build-libs
make css
```

先运行受影响模块的针对性检查，集成完成后跑一次完整要求：

```bash
make test
make lint
cargo check --locked --target wasm32-unknown-unknown --no-default-features --features web
```

`make lint` 已含 server/all-features 的 Clippy 检查；不要用只编译 server 代替 WASM 目标。用 `cargo fmt` 格式化 Rust，不例行执行 `dx fmt`。

浏览器检查针对现有开发服务运行；需要新服务时先核对端口、工具及 `.env`，按 `make dev` 启动并记录此次启动的进程，避免覆盖其他任务的服务。

新脚本的建议调用约定：

```bash
SHOWCASE_BASE=http://127.0.0.1:8080 node scripts/test-components-showcase.cjs
```

地址必须与本地实际配置一致。有导航、目录或布局共用代码变更时，再按 `scripts/README-view-transitions.md` 执行受影响的既有回归。开发数据或凭据不足导致的未运行项要单独列明。
