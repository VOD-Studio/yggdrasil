# rua.plus 首屏性能实测（v1.1.1，2026-10-28）

线上版本 `v1.1.1`（`685a1b4f`），经 EdgeOne 访问 `https://rua.plus`。这是优化前的基线。

## 测量方法

- 工作站 headless Chromium，每次新建浏览器上下文、禁用缓存，取 3 次中位数。
- 桌面：1440×900，不限速。
- 移动：390×844、DPR 3，1.6 Mbps / 150 ms RTT，CPU 降速 4 倍。
- 「去 preload」：拦截 HTML，删除全部 `<link as="fetch" rel="preload" type="application/wasm">` 后再加载。
- 水合完成：`html[data-hydrated]` 出现的时间（`performance.now()`）。
- 工作站流量经过本地透明代理（fake-IP 198.18.x），同一路由多轮之间有明显波动，表中数据只看趋势。

## 发现的问题

1. **WASM preload 泛滥。** `/` 的 `<head>` 里有 363 个 `<link rel="preload" as="fetch" type="application/wasm">`，去重后 270 个，单个文件最多重复 5 次，占原始 HTML 51 KB（全文 125 KB）。来源是 `leptos_integration_utils-0.8.9/src/lib.rs:77-94`：每个预取的 lazy fn 都把清单里的全部分包展开成 preload，不去重；第 90 行还把 nonce 填进了 `crossorigin`。弱网下这些 preload 和 CSS 抢带宽：去掉后移动端 FCP 减少 0.5–2.5 s，水合完成时间不变。`/post` 不输出这些链接。
2. **主入口每次整包下载。** `/pkg/yggdrasil.*.wasm`（brotli 317,693 B）和 `.js` 返回 `cache-control: public, no-cache`。源站对 `If-None-Match` 返回 304，但经过 EdgeOne 一律返回 200 加完整包体（EdgeOne 不缓存 `no-cache` 资源，也不把条件请求转给源站），回访用户每打开一个页面都重下 317 KB。
3. **分包过碎。** 每个页面请求 330–700 个 WASM 分包，大多不到 1 KB；水合完成桌面 0.8–3.7 s，移动 3.8–6.9 s。
4. **EdgeOne 配置**（`tccli teo DescribeL7AccSetting` / `DescribeL7AccRules`）：缓存遵循源站；缓存键为完整 URL（`?v=` 能失效缓存）；QUIC 关闭；一条规则把 `jpg/png/gif/bmp/svg/webp` 的浏览器缓存统一改成 3600 s；HTML 在 EdgeOne 一直 MISS，由源站 SSR 缓存兜底。

## 优化与本地对照

针对上面的问题做了三项改动（EdgeOne 另见下一节）：

1. `app::HydrationScriptsWithoutSplitPreload` 取走 `WasmSplitManifest`，HTML 只预载主包 wasm 和分包加载器。
2. `build-release.ts` 按入口 JS、主 wasm、加载器三者的最终内容重新命名，`hash.txt` 写入 `entry: content-addressed`，服务端据此对入口返回 `immutable`。
3. cargo-leptos 改用分包合并补丁版 wasm-split（`VOD-Studio/wasm-split-prototype` 的 `ygg/chunk-merge`，`8ca741dd`）。

对照方法：同一份服务端与 Rust 产物，只用 `WASM_SPLIT_CHUNK_LOAD_COST=0` 关闭合并重新构建前端，得到「未合并」组。两份 release 各起一个服务端，连本机开发库，前面套一个本地 HTTP/2 TLS 代理（避免 HTTP/1.1 的 6 连接限制放大请求数的影响）。冷缓存，每格取 3 次中位数。两组都已去掉分包 preload，所以这里只比较分包合并的效果。

## EdgeOne 调整（2026-10-28，`tccli teo`）

改动前的配置备份在工作站 `~/.local/share/ygg-ha/edgeone-backup-20261028/`。

- 删除规则引擎里把 `jpg/png/gif/bmp/svg/webp` 浏览器缓存统一改成 3600 s 的子规则，浏览器缓存改为遵循源站：`/uploads/` 恢复为源站给的 `public, immutable, max-age=31536000`。
- 开启 QUIC，响应带 `alt-svc: h3=":443"`。
- 入口文件不需要额外规则：内容寻址后源站返回 `immutable`，按「遵循源站」即可在节点缓存。

第二轮（同日，备份在 `~/.local/share/ygg-ha/edgeone-backup-20261028-1818/`）：

- AI 爬虫处置（`BotManagementLite.AICrawlerDetection`）由托管挑战改为观察（Monitor）。原先 `GPTBot`、`ClaudeBot`、`Claude-User` 访问任何路径（包括 `POST /mcp` 与 `/feed.xml`）都只拿到约 990 B 的 `EO_Bot_Ssid` 挑战脚本，AI 客户端连不上 MCP，也无法代用户读文章。想按路径加例外规则，`ModifySecurityPolicy` 对任何 `ExceptionRules` 都返回 `InvalidParameter`（官方示例原样提交也失败，个人版套餐疑似不支持），因此改为全站观察，仍记录日志。
- HTTP→HTTPS 跳转由 302 改为 301。
- HSTS 由 `max-age=16070400; preload` 改为 `max-age=31536000`：preload 标记要求一年且 includeSubDomains，原配置并不满足；子域未确认全部 HTTPS，不开 includeSubDomains。
- 未改：WAF 托管规则保持仅观察（后台提交的 Markdown/代码易误判）；源站防护（只放行 EdgeOne 回源 IP）需要同时改两台服务器防火墙，未开启；源站组仍是手动切换权重。

## 第二轮：小文件为什么要几百毫秒（2026-10-29）

线上 `v1.2.0` 的开发者工具里，首页几十个 1–5 KB 的 `.wasm` 每个都显示 115–210 ms，个别 450–510 ms。

- **EdgeOne 大致逐个处理同一客户端的并发请求。** 在同一条 h2 连接上请求首页的 59 个分包（全部 `eo-cache-status: HIT`），串行时每个约 5 ms；并发 1/10/20/40/59 个时，中位耗时分别为 6/20/35/88/117 ms，基本按每个约 2 ms 线性增长。开发者工具里每个请求的耗时都从它发出时算起，排在后面的自然显示 200 ms 上下。
- **分包要等主包实例化后才发出。** 无头 Chromium 冷加载首页时，主 wasm 在 121 ms 下载完；59 个分包在 298–317 ms 才发出，TTFB 从 87 ms 排到 205 ms，约 511 ms 全部到齐。
- **450–510 ms 的是回源。** 同一个 immutable 分包 75 分钟内回源 3 次：各节点各自缓存，新版本发布后的第一批访客要逐个回源。（当时以为 EdgeOne 按 `Accept-Encoding` 分别缓存 br 与 gzip，后来证实不对，见文末「EdgeOne 预热导致 br 变大」。）
- **源站复用连接慢 40 ms。** 回源日志的 `request_time` 只有 0.001 和 0.041 两档。在 xun 上对 app 用同一 keepalive 连接连发请求，第一次 1 ms，之后每次 41 ms：`axum::serve` 没有设置 `TCP_NODELAY`，hyper 分两次写响应头和包体，第二次写要等 nginx 的延迟 ACK。
- **全局样式每次回源。** `style.css`、`highlight.css`、`katex.min.css`、`yggdrasil-core.{css,js}` 返回 `no-cache`，EdgeOne 每次都 MISS，TTFB 65–363 ms，而且都在首屏关键路径上。EdgeOne 缓存键是完整 URL（开了 `FullUrlCache`，`?zz=1` 实测单独缓存），所以带内容版本号的地址可以 immutable。

### 改动

1. `WASM_SPLIT_CHUNK_LOAD_COST=8192`（Makefile 的 `build-frontend`）。
2. `app::HydrationScriptsWithPreload`：按请求路径只为当前路由的视图分包输出 `<link rel="preload" fetchpriority="low">`。第一版没加 `fetchpriority`，FCP 在移动档变慢 0.4–1.2 s（与上一轮 preload 泛滥同一原因：和 CSS 平分带宽）；改成低优先级后 FCP 与基线持平。
3. `static_assets`：固定路径资源地址带内容摘要 `?v=`，版本一致时 `immutable`。
4. 接入连接设置 `TCP_NODELAY`。
5. `scripts/edgeone-prefetch.ts`：发版后把线上首页引用的分包、入口与版本化资源预热到 EdgeOne 中间层。v1.2.1 部署后发现它让 br 变大，已删除，见下文。

## v1.2.1 线上复测与 EdgeOne 预热问题（2026-10-29）

### 冷加载

工作站无头 Chromium，禁用缓存，直开首页，每版 1–5 次。「水合」指 `html[data-hydrated]` 出现的时间；「路由分包」是水合前请求的分包数。

| 版本 | TTFB | DCL | FCP | 路由分包 | 分包发出 → 到齐 | 单个分包最大 TTFB | 水合 | 水合后空闲预取 |
|---|---|---|---|---|---|---|---|---|
| v1.2.0 | 82 | 432 | 456 | 61 | 491 → 888 | 316 | > 888 | 约 100 个 |
| v1.2.1 | 46–135 | 95–262 | 176–276 | 20 | 54–143 → 186–360 | 43–176 | 271–402 | 19 个 |

时间单位 ms。v1.2.0 的分包要等主包实例化才发出（491 ms），排队时间随数量线性增长，最慢的排到 316 ms；v1.2.1 的分包随 HTML 里的低优先级 preload 和主包一起发出，数量为原来的三分之一。

### EdgeOne 预热导致 br 变大

v1.2.1 部署后，在 CDN 上用 `Accept-Encoding: br` 请求 159 个 `/pkg/` 文件，有 105 个比源站的 `.br` 大 10–25%（主 wasm 395,543 B，源站 315,698 B），而且全部是 `HIT`。部署刚完成时，主 wasm 的 br 请求连续 16 秒是 0 字节，页面一直没有水合。

- xun 的 nginx 日志里，预热任务对每个文件先发 1 字节的 Range 探测，再从约 14 个节点各发一次 Range 请求，全部返回 `206` 和未压缩的字节数。`CreatePrefetchTask` 的 `Headers: Accept-Encoding: br` 没有作用。
- 节点缓存的是未压缩版本时，浏览器请求 br 拿到的是 EdgeOne 用自己的压缩（站点「智能压缩」开着 brotli/gzip）压出来的结果，压缩率不如源站 quality 11 的 `.br`，并且之后一直以 `HIT` 返回这个大小。复现：清除 `chunk_65` 的缓存，先发一次不带 `Accept-Encoding` 的请求，之后的 br 请求一直返回 3795 B（源站 3246 B）；如果第一次就是 br 请求，节点缓存的是源站的 `.br`，大小一致。
- 规则引擎对 `wasm/js/css` 关闭分片回源后，普通回源变成 `200`，但预热任务仍然用 Range 拉取，节点仍缓存未压缩版本。改配置解决不了，规则已还原（备份在工作站 `~/.local/share/ygg-ha/edgeone-backup-20261029/`）。

处理：`purge_prefix https://rua.plus/pkg/` 后，159 个文件的 br 大小全部与源站一致；删除预热脚本、`deploy.fish` 中的调用和 CI 的 `prefetch-cdn` 作业，并删除仓库变量 `EDGEONE_ZONE_ID`。以后由浏览器请求触发回源，各节点第一次回源多花的时间换来源站 `.br`：从 rua 直连 xun 拉主 wasm 的 br 约 1.2 s，未压缩约 5.9 s。
